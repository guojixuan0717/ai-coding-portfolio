# 任务设计与评估方法

本作品集用三个小型 Python 任务演示如何把数据处理需求转化为可检查的编码任务。核心是让规格足够明确，让正确性判断可复现，并使评分追溯到具体行为。它不是模型训练系统，也没有模型训练或提升效果的证据。

## 从规格到评分

每题明确函数签名、输入类型、输出结构、顺序规则、异常类型、边界条件和复杂度目标。歧义应先在任务书解决，例如「按组比例」不是「按记录比例」，宏平均是否包含未出现的标签也必须写清。

测试由人工可理解的案例、错误输入和性质检查组成。预期值采用手工可核验结果或独立结构性质，不以参考实现输出作为测试真值。评分文件把每个 unittest 方法映射为正整数分值，每题总和 100；一个方法内的子测试共同承担该方法分值。全部子测试通过才获得该方法分数。

## 错误候选为何有用

每题另写三个具有明确缺陷的候选。若某候选通过所有测试，说明测试对该缺陷不敏感，或者对缺陷本身的定义有误，应回到规格和测试复查。发现某个错误只表示至少一个测试失败，不能证明测试对同类所有缺陷都敏感。

起始桩统一抛出 NotImplementedError，用于验证评估流程能识别未完成实现。它不代表真实模型基线。参考实现和错误候选均公开，用于学习与展示，不用于保密测评。

## 可复现与证据

根目录 evaluate.py 为每个候选启动新的 Python 子进程，避免导入缓存串扰。进程设置 45 秒超时；报告保留环境、运行时间、源码哈希、测试状态与日志。测试前后哈希不一致时终止报告生成，避免把变化中的源码与结果混用。

这个子进程机制仅用于包内已知代码，不是安全沙箱。没有对不可信代码执行能力作出承诺。报告也不记录性能基准、网络隔离验证或多平台兼容性测试；目前只在报告列明的本地环境实际运行。

## 用于正式评估前的工作

任务作者需要独立复核规格和答案，新增保密测试，并确认训练数据与评测数据的来源边界。按组划分只能避免共享分组的泄漏，不能自动发现跨组的语义重复。公开题库本身也可能造成答案泄漏。

需要收集真实候选的输出后，才能讨论任务难度、区分度和通过率。未运行真实模型时，不应把人为错误候选的分数写成模型表现。若涉及人工评分，另需提供锚定样例并检查评分者一致性。
